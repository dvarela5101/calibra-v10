## Historia
Como **equipo de Calibra** quiero **comprobar en el servidor el contenido de cada comprobante, limpiar los que nunca llegan a un pago y limitar cuántos sube cada sesión** para **que el bucket privado no se llene de basura ni acepte archivos que no son lo que dicen ser**.

## Contexto
- **Tipo de usuario:** Tareas técnicas
- **Corte propuesto:** Corte 1 (MVP), antes de abrir la app al público
- **Épica:** E6 Pagos y verificación
- **Reglas:** RN-40, RN-41. Sección 14 (comprobantes).
- **Decisiones (29-sep-2026):** N-4: un comprobante sin pago se borra a las 24 horas, salvo que un pago lo use; cada sesión puede subir máximo 5 comprobantes cada 24 horas.

HU-007 dejó el bucket `comprobantes` funcionando, pero tres cosas quedaron fuera porque exceden su alcance:

- El Storage solo mira el tipo MIME que declara quien sube. La app contrasta los primeros bytes del archivo en el navegador, pero alguien que suba directo a la API puede declarar `image/png` y mandar otro contenido.
- Un archivo subido que nunca llega a un pago (la persona cierra la página, el pago se rechaza al crearse) queda huérfano en el bucket.
- Cualquier sesión anónima puede subir sin tope de cantidad; cada archivo pesa hasta 5 MB (10 MB después de [HU-063](HU-063.md)).

## Criterios de aceptacion
- [x] Dado un archivo subido directo a la API con un tipo declarado que no coincide con su contenido, cuando el servidor lo revisa, entonces se descarta y ningún pago puede apuntar a él.
- [x] Dado un comprobante que lleva más de 24 horas sin que ningún pago lo use, cuando corre la limpieza, entonces se borra con la API de Storage y la llave secreta. Un comprobante que un pago usa nunca se borra por esta limpieza.
- [x] Dado una sesión que ya subió 5 comprobantes en las últimas 24 horas, cuando intenta subir otro, entonces se rechaza con un mensaje claro.

## Fuera de alcance
- Lectura automática (OCR) del comprobante.
- Marcar como posible duplicado un `referenciaTransferencia` ya usado: descartado por ahora (D-38).

## Notas tecnicas
Borrar por SQL está bloqueado por Storage (`storage.protect_delete`): la limpieza usa la API con `service_role`. La revisión del contenido puede vivir en la función que crea el pago ([HU-018](HU-018.md)), que ya tiene que comprobar `rutaEsDelUsuario()`.

Cómo quedó.

Una migración nueva, `*_endurecer_comprobantes.sql`, y el código del servidor en `src/lib/comprobantes/`.

- **Contenido real.** `revisarComprobante()` (`revision.ts`; desde el servidor, `revisarComprobanteDesdeServidor()`) baja el archivo con la llave secreta y exige que los primeros bytes sean del tipo que se declaró al subir y del de la extensión. Si coinciden, lo anota con `anotar_comprobante_revisado()`. Si no, lo descarta: quita su fila de revisado y lo borra con la API de Storage, salvo que un pago ya lo use. `pago.comprobante` pasa a ser una llave foránea a `comprobante_revisado`, así que la base no deja crear un pago con un comprobante sin revisar o descartado. HU-018 debe llamar a la revisión antes de crear el pago.
- **Huérfanos.** `tomar_comprobantes_huerfanos()` elige, con el reloj de la base, los de más de 24 horas sin pago y en la misma sentencia les quita la fila de revisado; `limpiarComprobantesHuerfanos()` (`limpieza.ts`) los borra con la API de Storage. Como `anotar_comprobante_revisado()` no anota nada de más de 24 horas, la revisión y la limpieza nunca se cruzan. Corre cada hora: pg_cron llama a `/api/procesos/limpiar-comprobantes` con el secreto de HU-065 (`privado.disparar_proceso()`).
- **Cuota.** Un trigger sobre `storage.objects` cuenta las subidas de cada carpeta en `privado.subida_comprobante` y rechaza la sexta en 24 horas. Cuenta subidas, no archivos: un descartado sigue contando. Frena también las subidas con URL firmada, que no pasan por las políticas. `subirComprobante()` pregunta antes con `mi_cuota_de_comprobantes()` y dice desde cuándo se puede subir otro.

Cómo verificarlo: `npm run db:reiniciar`, `npm run db:verificar` (incluye `supabase/tests/comprobantes_endurecidos.test.sql`), `npm run test:integracion` (incluye `integracion/comprobantes-endurecidos.test.ts`) y `npm run verificar`. Si el stack local ya corría, `npm run db:detener` antes de `npm run db:iniciar`, para que tome el protocolo S3 apagado.
