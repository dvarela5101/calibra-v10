## Historia
Como **equipo de Calibra** quiero **el modelo de dominio v10 como migraciones versionadas, con sus restricciones y políticas de acceso** para **que las reglas se apoyen en la base de datos y no solo en la interfaz**.

## Contexto
- **Tipo de usuario:** Tareas técnicas
- **Corte propuesto:** Corte 1 (MVP)
- **Épica:** Transversal (sin épica propia)
- **Reglas:** RN-15, RN-21, RN-22, RN-33, RN-61, RN-62, RN-70, RN-80. Secciones 5, 10, 11 y 14.
- **Pendientes:** P-18 (relación Evaluación y temas), P-28 (desembolso anulado), P-33 (diagnóstico sin Lead). Las definiciones están en `calibra_reglas_negocio.md` §13 (P-01 a P-17) y en `REVISION_REGLAS.md` (P-18 en adelante).

El diccionario de datos (sección 10) y el diagrama (sección 11) son la fuente. La sección 14 recomienda montos como enteros en pesos, fechas con zona horaria, `dia` como número y `hora` como hora, y `MonitoriaGrupal` como tabla hija con la misma llave.

**Frente a la app actual.** El esquema del prototipo tiene 13 tablas más `monitores_aprobados` y `gate_intentos`. Las `franjas` son horas concretas de 1 h (no recurrentes), `citas` hace de Monitoria sin estados, `estudiantes` es uno por correo y `monitores` acepta inserción pública con una `clave` pública. No hay admin, pagos, reembolsos, desembolsos, reportes ni reseñas. Se diseña de cero; las tablas de contenido se retoman en [HU-005](HU-005.md).

## Criterios de aceptacion
- [x] Dado una base vacía, cuando se aplican las migraciones, entonces existen las tablas lead, estudiante, monitor, perfil_monitor, admin, materia, evaluacion, diagnostico, certificado, franja, monitoria, monitoria_grupal, pago, desembolso, reembolso, reporte_inasistencia y resena, y los enums de la sección 5.
- [x] Dado un certificado de un monitor en una materia, cuando se inserta otro para la misma pareja, entonces la base lo rechaza (RN-21).
- [x] Dado una monitoría no cancelada en una franja y fecha, cuando se inserta otra para la misma franja y fecha, entonces la base la rechaza; si la anterior está cancelada, la acepta (RN-33).
- [x] Dado Reseña, Reembolso, Desembolso, ReporteInasistencia y Estudiante, cuando se inserta un segundo registro para el mismo pago, monitoría o lead, entonces la base lo rechaza (sección 14).
- [x] Dado una franja de un monitor, cuando se inserta una monitoría con una materia en la que ese monitor no tiene certificado, entonces la base la rechaza (RN-22).
- [x] Dado un diagnóstico ligado a una monitoría, cuando su evaluación es de otra materia, entonces la base lo rechaza (RN-15).
- [x] Dado un usuario anónimo, cuando intenta leer leads, pagos, diagnósticos ajenos, reembolsos, desembolsos o reportes, entonces las políticas lo impiden; la lectura pública se limita a materias, evaluaciones, franjas y datos públicos del monitor.
- [x] Dado las migraciones ya aplicadas, cuando se vuelven a aplicar, entonces no fallan, y un script de verificación comprueba restricciones y políticas.

## Notas tecnicas
No se guarda `contrasenaHash`: las cuentas usan Supabase Auth y las tablas guardan el id del usuario de Auth. Los atributos derivados (`/x`) no se guardan: los calcula [HU-003](HU-003.md). Montos en `integer` (pesos), fechas en `timestamptz`.

Implementación (2026-09-28):
- Migraciones: `supabase/migrations/20260929022931_esquema_v10.sql` (enums, 18 tablas, restricciones, triggers) y `20260929022942_politicas_v10.sql` (RLS, permisos, funciones en el esquema `privado`). Idempotentes.
- Verificación: `npm run db:reiniciar` y `npm run db:verificar` (reaplica las migraciones y corre `supabase/tests/esquema_v10.test.sql`, 97 comprobaciones pgTAP). También corre en el job `base-de-datos` del pipeline.
- Solo en Supabase local (Docker). El proyecto real no se tocó: se aplica en el corte ([HU-057](HU-057.md)).
- `monitor_privado` es una tabla extra: contacto y llave del monitor fuera de la lectura pública.
