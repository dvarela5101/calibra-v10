## Historia
Como **equipo de Calibra** quiero **publicar el producto v10 terminado y pasar la base de datos del prototipo al modelo nuevo en un solo corte** para **que los estudiantes usen la versión nueva sin perder el contenido ni el historial del prototipo**.

## Contexto
- **Tipo de usuario:** Tareas técnicas
- **Corte propuesto:** Último, con el resto del backlog cerrado (decisión de la persona, 2026-09-28: "armar todo el producto y lo último, con el backlog vacío, desplegar").
- **Épica:** Transversal (sin épica propia)
- **Origen:** criterio de CI/despliegue de [HU-001](HU-001.md), movido aquí, y la estrategia de base de datos decidida al iniciar [HU-002](HU-002.md).

Estrategia de base de datos acordada: **mismo proyecto Supabase (`uotlhaitdkfroavqkvee`), con corte planificado.** v10 se desarrolla y prueba en Supabase local (Docker) con migraciones versionadas en `supabase/migrations/`. El proyecto real no se toca hasta este corte, porque el prototipo (`../Calibra/index.html`) debe seguir funcionando hasta entonces.

Inventario del proyecto real (2026-09-28): 15 tablas en `public`, todas con RLS, sin migraciones registradas, sin usuarios de Auth ni buckets. Contenido: 8 materias, 35 subtemas, 135 preguntas, 540 opciones, 18 knowledge components, 56 misconcepciones. Uso (20 al 24 de septiembre): 25 leads (todos con correo, 13 con teléfono, sin autorización de datos), 41 diagnósticos (8 ligados a un lead), 5 monitores, 14 franjas y 2 citas, ya vencidas.

Qué se lleva al modelo v10:
- Contenido: sí, a las tablas del banco (ver [HU-005](HU-005.md)).
- Monitores: no como cuentas. Se invitan (HU-013) y se pueden precargar perfil y certificados.
- Leads: no como contactables, porque no autorizaron el tratamiento de datos ([HU-008](HU-008.md)). Se quedan en el archivo.
- Diagnósticos: se quedan en el archivo para análisis. Importarlos como históricos sin lead es opcional.
- Franjas y citas: no; eran de prueba y ya vencieron.

## Criterios de aceptacion

- [ ] Dado el proyecto Supabase real, cuando se ejecuta el corte, entonces antes de cambiar nada existe un respaldo descargado de la base.
- [ ] Dado el corte, cuando se ejecuta, entonces las 15 tablas del prototipo pasan a un esquema `prototipo` no expuesto por la Data API, con sus datos intactos (mismos conteos antes y después).
- [ ] Dado el esquema `prototipo`, cuando se aplican las migraciones de `supabase/migrations/`, entonces `public` queda con el modelo v10 y el script de verificación de HU-002 pasa contra la base real.
- [ ] Dado el contenido archivado, cuando corre el script de migración de datos, entonces materias, temas, preguntas, opciones, knowledge components y misconcepciones quedan en las tablas v10 con los mismos conteos, y ningún lead del prototipo queda como contactable.
- [ ] Dado el corte terminado, cuando se abre la URL de producción, entonces la app v10 funciona contra la base real, y el prototipo queda fuera de línea o avisa que fue reemplazado.

## Notas tecnicas
- Repo: el código vive temporalmente en `dvarela5101/calibra-v10` (público). En el corte se sube al repo real con historial: `git remote add calibra https://github.com/Juzou04/Calibra.git` y `git push calibra main:v10`. Después `v10` pasa a ser la rama principal, el prototipo queda en una rama `prototipo` y el repo temporal se archiva. Issues y PRs del temporal no viajan.
- El `supabase/schema.sql` del prototipo empieza con `drop table ... cascade`: nunca se corre sobre el proyecto real.
- Mover tablas con `alter table ... set schema prototipo` conserva datos, índices y restricciones. Las funciones `reservar_franja` y `publicar_franjas` y la vista `brief_cita` del prototipo también se mueven o se eliminan.
- Revisar si el proyecto tiene la integración de GitHub de Supabase conectada al repo del prototipo: `list_branches` muestra una rama `main` con `git_branch: main`. Si es así, desconectarla o reconectarla al repo nuevo antes de subir migraciones.
- El webhook del correo y la Edge Function `enviar-correo` del prototipo se desactivan en el corte.
- Auth del proyecto real (desde HU-004; hoy solo está en `supabase/config.toml` local):
  - Activar el inicio de sesión anónimo, contraseña mínima de 8 caracteres, `site_url` de producción y las URL de redirección.
  - Plantilla de recuperación `supabase/templates/recuperar.html`. Desde el 3-jun-2026, un proyecto Free con el SMTP por defecto no puede personalizar plantillas: hace falta un SMTP propio (ver HU-006, dominio verificado).
  - Límites de tasa por defecto (30 anónimos por hora por IP). Considerar CAPTCHA en el inicio anónimo, como recomienda Supabase.
  - Desde el 30-oct-2026 la nube no expone tablas sin `grant` explícito. Las migraciones ya los dan.
- Semilla (desde HU-012): `supabase/seed.sql` crea `admin1@calibra.test` y `admin2@calibra.test` con una contraseña que está en el repo público. Nunca usar `supabase db push --include-seed` contra el proyecto real. Después del corte, comprobar que no existe ninguna cuenta `@calibra.test` y cargar la lista real de admins con su orden de revisión.
- Correo (desde HU-006): cuenta de Resend con el dominio verificado (SPF y DKIM) y una llave de solo envío. En Vercel van `RESEND_API_KEY`, `CORREO_REMITENTE` (`Calibra <hola@dominio>`) y `SITIO_URL` con https; `MAILPIT_URL` no se carga. El criterio 2 de HU-006 (que el correo llegue a una cuenta externa) se comprueba aquí, enviando una plantilla a una cuenta del equipo. Revisar también la cuota del plan de Resend.
