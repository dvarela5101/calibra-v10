  - N-6: el desembolso se puede ejecutar solo después de que venza la ventana de reporte.

HU-003 y HU-007 se aprobaron el 29-sep-2026 con estos ajustes pendientes, que salieron de una revisión criterio por criterio. Ninguno era un fallo de seguridad de alta gravedad.

## Criterios de aceptacion
- [x] Dado una sesión `anon` o `authenticated`, incluida una anónima, cuando llama por RPC `comision()`, `monto_neto()` o la función que devuelva los parámetros de comisión, entonces recibe un error de permisos (42501). `service_role` sí puede. Los parámetros de plazo siguen disponibles para `authenticated`, así que los plazos no se rompen.
- [x] Dado el instante exacto de fin + 24 h, cuando se evalúan los plazos, entonces el reporte de inasistencia sigue abierto y el desembolso todavía no es ejecutable. Lo es solo después de ese instante, en SQL y en TypeScript, con pruebas de borde.
- [x] Dado `ventana_resena_hasta` con fecha de finalización vacía, cuando se llama en SQL, entonces se comporta igual que en TypeScript (rechaza), con una prueba en cada lado.
- [x] Dado las funciones de parámetros, `comision()` y `monto_neto()`, cuando se definen, entonces son `stable` y no `immutable`, porque sus valores cambian por migración.
- [x] Dado un comprobante de hasta 10 MB, cuando se sube, entonces se acepta; si pesa más, se rechaza con un mensaje claro. El bucket y `src/lib/comprobantes/reglas.ts` dicen lo mismo, y una prueba lo contrasta.
- [x] Dado un comprobante ajeno, cuando alguien intenta reemplazarlo con `move`, `copy` o una URL de subida firmada con `upsert`, entonces no puede, y hay pruebas de integración que lo verifican.
- [x] Dado el README, cuando alguien levanta Supabase local, entonces encuentra la advertencia: si el stack ya corría sin Storage, hay que correr `npm run db:detener` antes de `npm run db:iniciar`.

## Notas tecnicas
- Todo va en migraciones nuevas: no se editan las de HU-003 ni HU-007, que ya están en `main`.
- Separar los parámetros de comisión de los de plazo, por ejemplo con `parametros_comision()`. Cambiar el tipo de salida de `parametros_negocio()` exige `drop function` antes de recrearla.
- Ajustar `ParametrosNegocio` y `calcularComision` en TypeScript, y cambiar `integracion/plazos.test.ts` para que espere 42501 donde hoy espera la cifra.
- Si P-32 termina mostrando la comisión al monitor, que sea con una vista de su propio desembolso y no por RPC.

Cómo quedó.

Dos migraciones nuevas, sin tocar las de HU-003 ni HU-007.

`*_ajustes_plazos_y_comision.sql`:
- `parametros_negocio()` devuelve solo los 11 plazos y `parametros_comision()` devuelve el porcentaje y el tope. `comision()`, `monto_neto()` y `parametros_comision()` solo las ejecuta `service_role`; con una sesión anónima, de monitor o de admin, la RPC responde 42501.
- `desembolso_ejecutable(fin, ahora)` compone las dos comparaciones de P-40: el plazo de desembolso se alcanzó y ya no se está dentro de la ventana de reporte. En el instante exacto fin + 24 h el reporte sigue abierto y el desembolso no es ejecutable. La vista `desembolsos_ejecutables` de la bandeja usa esa función.
- `ventana_resena_hasta(null)` lanza 22004, igual que `ventanaResenaHasta(null)` en TypeScript. La vista `monitoria_plazos` ya no la llama para una grupal sin finalizar.
- Las funciones que leen parámetros pasan a `stable`.

`*_ajustes_comprobantes.sql`: el bucket sube de 5 a 10 MiB.

En TypeScript: `ParametrosNegocio` ya no trae la comisión; `ParametrosComision` y `cargarParametrosComision()` (solo funciona con la llave secreta) la reemplazan; `desembolsoEjecutable()` es el gemelo de la función SQL; `LIMITE_COMPROBANTE_BYTES` vale 10 MiB.

Comprobantes ajenos: `move`, `copy` y las URL de subida firmadas con `upsert` ya fallaban contra el comprobante de otra persona. No hizo falta una política nueva; se agregaron las pruebas de integración que lo verifican. Al explorarlo apareció un caso del propio dueño, que queda en [HU-067](HU-067.md).

`scripts/verificar-bd.mjs` ganó una lista de preámbulos. La HU pide `drop function` sobre `parametros_negocio()`, y con eso `db:verificar` ya no podía reaplicar la migración vieja de plazos sobre la base final. El preámbulo borra la función antes de reaplicar esa migración, así no se edita la migración que está en `main`.

Cómo verificarlo: `npm run db:reiniciar`, `npm run db:verificar`, `npx supabase db advisors --local --level warn`, `npm run test:integracion` y `npm run verificar`.
